# 03-03 Admin proof review

Status: planned. Depends on 03-02. Owners: OPER-05, PAY-05, PAY-06, PAY-08, UX-02.

User story: from my phone I see which proofs wait, check one against the booking, and approve or reject it in a tap or two; the member and the schedule follow.

- [ ] `GET /api/admin/bookings?status=review` (oldest first), `reviewCount` beside `unpaidCount`; booking detail with proofs, files and payment records; approve/reject endpoints with `version` and the outcome. OpenAPI `03-03-OPENAPI.yaml`.
- [ ] Booking masuk: "Perlu dicek" filter first, with its count; the rail/dock Booking badge shows the review count when there is one (else unpaid, as today).
- [ ] Review view: phone full screen (board 15 pattern), desktop drawer (D6): booker, participants, expected total, submitted at, original deadline and time left, state; the proof files (images inline, tap to zoom with pinch; PDF opens in a new tab); earlier submissions collapsed.
- [ ] Approve: one tap; toast "Pembayaran {name} dikonfirmasi."; the booking moves out of Perlu dicek with the row marker gliding to the next one on desktop.
- [ ] Reject: a sheet (phone) / dialog (desktop) with the four reasons (Lainnya needs text); after reject the detail offers "Chat {name}" (WhatsApp, prefilled with the reason and time left or the release); toast "Bukti ditolak." or, after the deadline, "Bukti ditolak, slot dilepas."
- [ ] Version conflicts and races (two admins, member resubmits meanwhile) end in one notice panel with the latest state.
- [ ] Tests: approve/reject transitions and versions; reject before vs after deadline (release); approve on a cancelled session refused; queue order and counts; privacy of admin file routes; admin review on a phone at 390 with no sideways scroll.

Acceptance: an admin can clear the review queue entirely on a phone; the member sees Lunas or Perlu diperbaiki with the reason; capacity matches every outcome.
