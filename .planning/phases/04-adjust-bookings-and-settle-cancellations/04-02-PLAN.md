# 04-02 Session cancellation and contact checklist

Status: planned. Depends on 04-01. Owners: CANC-01, CANC-07.

User story: it rains, or only two people booked; from the roster I cancel the session, see exactly who is affected and what is owed, and tick off each booker as I message them.

## Tasks

- [ ] Migration (after `npm run db:backup`): `ClassSession.cancelledAt/cancelledById/cancelReason/cancelNote`; `SessionContact`.
- [ ] `server/features/admin/sessions/session-cancel.service.ts`: preview (places, bookings, paid bookings, refunds due) and cancel in one transaction: session `cancelled`, every active booking `cancelled` with `session_cancelled` through the 04-01 booking-cancel logic (shared, not copied), refunds for paid ones, one change event per booking, a `SessionContact` row per affected booking. Version check on the session; `SESSION_STARTED` after start. Routes in `sessions.router.ts`, handlers in `session.controller.ts`. OpenAPI `04-02-OPENAPI.yaml`.
- [ ] Session editor: the existing cancelled state stays read-only; editing a cancelled session is refused (already) and its copy points to "Terbitkan sesi baru".
- [ ] Roster screen (`SessionRosterPage`) and desktop roster panel (`RosterPanel`): Batalkan sesi (destructive, secondary placement). Confirm sheet/dialog: reason chips (Peserta kurang · Cuaca · Lapangan tidak tersedia · Lainnya, free text for Lainnya) and the effect line ("8 slot dari 4 booking dibatalkan. 2 booking sudah bayar: refund Rp 600.000.").
- [ ] After cancel: the roster becomes the contact checklist: each affected booker with the WhatsApp button (prefilled message with the reason and refund, if any) and a Sudah dihubungi tick (`PUT .../contacts/:bookingId`). Admin Sesi day list shows the session as Dibatalkan.
- [ ] Member: bookings show Dibatalkan with "Sesi dibatalkan: {reason}"; the public schedule, session detail, Pesan sheet and albums treat the session as cancelled (existing behaviour, re-verified).

## Tests

- Integration `tests/integration/session-cancel.test.ts`: preview counts match; cancel releases every place and blocks new bookings (admission refuses); each active booking cancelled with the right refund (unpaid none, paid full, under review `needsCheck`); expired bookings untouched; after start refused; version conflict; replay; contacts created and toggled; members see the reason only on their own bookings.

## Acceptance

From a phone, an admin cancels a session for low participation, sees the effect before confirming, then works through the contact checklist; members see the cancellation and their refund line; the session takes no bookings.
